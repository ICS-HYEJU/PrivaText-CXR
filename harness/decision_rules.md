# Decision Rules — 메트릭 미달 시 원인 진단 및 조정 규칙

> **이 문서가 하네스의 핵심입니다.**
> "메트릭이 나쁘니 알아서 분석하라"고 두면 LLM은 매번 다른 진단을 내놓아 실험이 재현되지 않습니다.
> 진단은 **결정 테이블**로 고정하고, 에이전트의 자유도는 "어떤 규칙이 발동했는가"를 판정하는 데까지로 제한합니다.
>
> 규칙에 해당하지 않는 상황(`D-99`)에서는 **에이전트가 추측으로 파라미터를 바꾸지 않고 사람에게 보고합니다.**

---

## 0. 판정 절차

매 평가 시점(T1 종료 시 / T2의 `save_every` epoch마다) 다음 순서로 처리합니다.

1. **트립와이어**(§1) 검사 → 위반 시 즉시 abort, 이후 단계 생략
2. **진단 규칙**(§2)을 D-01부터 순서대로 검사 → **첫 번째로 매칭되는 규칙 하나만** 채택
3. 채택된 규칙의 `action`을 `hparam_space.json`의 범위/step_rule 안에서 적용
4. `runs/<run_id>/analysis.md`에 기록(§4 템플릿)
5. 다음 런 실행

**규칙은 위에서부터 우선순위 순입니다.** 여러 개가 동시에 매칭되어도 하나만 적용합니다
(루프 5번 "한 번에 하나씩 조정" 원칙).

---

## 1. 트립와이어 — 즉시 런 중단

5일 런에서 실패를 조기에 잡는 것이 T2 자동화의 존재 이유입니다.

| ID | 조건 | 검사 시점 | 조치 |
|----|------|----------|------|
| **TW-01** | `train_loss` 또는 `val_loss`가 `NaN`/`Inf` | 매 로그 | abort. `status.json` → `failed(nan)` |
| **TW-02** | `epsilon_spent > target_epsilon` | 매 epoch | abort. **품질과 무관하게 실패**(C-01) |
| **TW-03** | `val_loss`가 최초 epoch 값 대비 2배 초과 | epoch ≥ 2 | abort(발산). D-01로 진단 |
| **TW-04** | `val_loss`가 연속 `max(5, epochs*0.15)` epoch 동안 개선 없음(상대 개선 < 0.5%) | epoch ≥ 10 | abort(정체). D-02/D-03으로 진단 |
| **TW-05** | GPU 프로세스 사망 / 6시간 이상 `metrics.jsonl` 미갱신 | 폴링 시 | `failed(stalled)` 보고. **자동 재시작 금지** — OOM/노드 문제일 수 있음 |
| **TW-06** | 디스크 여유 < 10GB | 폴링 시 | 경고 보고. 오래된 T0/T1 체크포인트 정리 제안 |

> **TW-04의 가치**: 1.24h/epoch에서 15 epoch 정체를 감지하면 약 **4일을 절약**합니다.

## 2. 진단 규칙

### D-01 — 학습 발산 (diverging)

**증상**
```
val_loss가 단조 증가 (연속 3 epoch 이상)
또는 TW-03 발동
또는 train_loss가 초기 대비 증가
```

**원인 가설** (가능성 순)
1. `lr`이 DP 노이즈 규모 대비 과대
2. `max_grad_norm`(C) 과대 → 클리핑이 사실상 작동하지 않아 노이즈 대비 업데이트가 불안정
3. `warmup_steps` 부족

**조치** — 순서대로 1회씩
1. `lr` → `x0.5`
2. (재발 시) `max_grad_norm` → `x0.5`
3. (재발 시) `warmup_steps` → `x2`

**주의**: DP-SGD의 발산은 non-private과 원인이 다를 수 있습니다. σ가 크면 gradient가 거의 노이즈이므로
lr을 줄여도 수렴하지 않고 정체(D-03)로 전환될 수 있습니다. 그 경우 D-03 규칙으로 넘어갑니다.

---

### D-02 — 과적합 (train↓ / val↑)

**증상**
```
train_loss는 계속 감소하는데 val_loss는 증가 또는 정체
gap = val_loss - train_loss 가 지속 확대
```

**원인 가설**
1. 학습 파라미터 대비 데이터 부족
2. 정규화 부족

**조치**
1. `unet_dropout` → `+0.05`
2. (재발 시) `ablation_blocks` 감소(더 적은 블록만 학습) → `-2`
3. (재발 시) early stop epoch을 gap 최소 지점으로 고정

**⚠ DP 맥락 주의**: DP-SGD는 노이즈 주입 자체가 강한 정규화입니다. **ε이 작은 설정에서 과적합이
관측되면 그 자체가 이상 신호**이며, DP가 제대로 적용되지 않았을 가능성을 먼저 확인하십시오
(σ가 0에 가깝지 않은지, `privacy_engine`이 실제로 optimizer를 감싸고 있는지).

---

### D-03 — 클리핑 포화 (DP 고유)

**증상**
```
clipped_frac ≈ 1.0  (거의 모든 샘플의 gradient가 클리핑됨)
AND val_loss 정체
```

**원인 가설**
`max_grad_norm`(C)이 실제 gradient norm 분포 대비 지나치게 작음.
모든 gradient가 같은 크기로 잘려 **방향 정보만 남고 크기 정보가 소실**됨.

**조치**
1. `max_grad_norm` → `x2` (`grad_norm_pre_clip`의 median 근처를 목표로)
2. 목표: `clipped_frac`이 0.3~0.7 구간

**전제**: 이 규칙은 `grad_norm_pre_clip` / `clipped_frac`이 로깅되어야 작동합니다
(→ `feature_list.json` F-03). **F-03 구현 전에는 D-03을 판정할 수 없으므로 D-99로 처리합니다.**

---

### D-04 — 노이즈 지배 (DP 고유)

**증상**
```
clipped_frac < 0.1  (클리핑이 거의 안 걸림 = C가 충분히 큼)
AND val_loss 정체
AND noise_multiplier(σ)가 큼
```

**원인 가설**
per-sample gradient의 실제 크기 대비 주입 노이즈가 커서 학습 신호가 묻힘.
DP 유틸리티 문제의 전형적 형태.

**조치** — 신호 대 잡음비를 올리는 방향
1. `logical_batch` → `x2` (배치가 클수록 노이즈 평균화 이득)
2. (재발 시) `ablation_blocks` 감소 → 학습 파라미터 수 축소 → 동일 ε에서 파라미터당 노이즈 감소
3. (재발 시) `finetune_biobert` → `false`
4. (재발 시) **LoRA 도입 검토** (F-06). 이 상황에서 가장 근본적인 해법이며 부수적으로 5일 런 시간도 단축됨

---

### D-05 — 초기 손실 이상 (scale 문제)

**증상**
```
epoch 1의 val_loss가 예상 범위 밖 (극단적으로 크거나 ~0에 가까움)
또는 학습 시작부터 loss가 거의 변하지 않음
```

**원인 가설**
1. latent scale 미정규화 → `scale_factor` / `scale_by_std` 문제
2. VAE 체크포인트 로딩 실패 (`--vae_ckpt` 미지정 시 random weight로 진행됨, `LDM_dp_finetune.py:510`)
3. `--pretrained_ckpt` 미지정 (`:542`)

**조치** — **하이퍼파라미터를 바꾸기 전에 로그를 먼저 확인**
1. `stdout.log`에서 `[VAE] WARNING: no --vae_ckpt` / `[LDM_dp] WARNING: no --pretrained_ckpt` /
   `[VAE ckpt] missing=` 값 확인
2. missing key가 10% 초과면 체크포인트 비호환 → **파라미터 튜닝이 아니라 설정 오류**. 사람에게 보고
3. 위가 정상이면 `--scale_by_std` 활성화 후 재시도

> 이 규칙이 D-01~D-04보다 뒤에 있지만, **T0/T1 첫 런에서는 항상 먼저 확인**하십시오.
> 대부분의 초기 실패는 하이퍼파라미터가 아니라 체크포인트 경로 문제입니다.

---

### D-06 — ε 예산 초과 위험

**증상**
```
epsilon_spent 추세를 외삽하면 학습 종료 전 target_epsilon 도달
```

**원인 가설**
`epochs` × `sample_rate` 조합이 예산 대비 과다.

**조치** — **`target_epsilon`을 올리는 것은 금지**(hparam_space policy)
1. `epochs` 감소 → 동일 ε에서 σ 감소 → 스텝당 품질 개선
2. `logical_batch` 조정으로 `sample_rate` 재조정
3. 어느 쪽도 기준을 못 맞추면: **현재 ε 예산에서 이 아키텍처로는 목표 달성 불가**라는 결론을
   기록하고 사람에게 보고. 이는 실패가 아니라 **유효한 실험 결과**입니다.

---

### D-99 — 규칙 미매칭

**조건**: D-01~D-06 어디에도 해당하지 않음.

**조치**
1. **파라미터를 임의로 바꾸지 않습니다.**
2. `analysis.md`에 관측된 메트릭 패턴을 기록
3. 사람에게 보고하고 새 규칙 추가를 제안

> 이 규칙이 자주 발동하면 결정 테이블이 부실하다는 뜻입니다. 이 문서를 갱신하십시오.

## 3. 승격 규칙 (T1 → T2)

T2는 5일을 소모하므로 승격은 보수적으로 판단합니다.

**T2 승격 조건 — 모두 만족해야 함:**
1. T1 런이 트립와이어 없이 완주
2. T1 `val_loss`가 현재 베이스라인 대비 개선
3. `epsilon_spent` 추세 외삽이 예산 내
4. 동일 설정 T1이 **2회 재현**되었거나, 개선 폭이 런간 분산보다 명확히 큼
5. **사람의 명시적 승인** ← 자동 진행 금지

**승인 요청 시 제시할 내용:**
- T1 결과 비교표 (베이스라인 vs 후보)
- 변경된 하이퍼파라미터와 그 근거가 된 규칙 ID
- 예상 소요 시간 및 ε 추정치
- 실패 시 조기 중단이 예상되는 시점

## 4. `analysis.md` 기록 템플릿

루프 4번("원인 분석 및 기록")의 산출물. 모든 런에 대해 작성합니다.

```markdown
# Run <run_id>

- **tier**: T1
- **started / ended**: 2026-08-03T10:15:00Z / 2026-08-03T14:02:00Z (3h47m)
- **base_run**: <직전 비교 대상 run_id>
- **changed**: `lr` 1e-4 → 5e-5  (단일 변경)
- **change_reason**: D-01 (발산) — 규칙 1단계 적용

## 결과
| metric | baseline | this run | Δ | threshold | pass |
|--------|----------|----------|---|-----------|------|
| val_loss | 0.1975 | 0.1802 | -0.0173 | TODO | – |
| epsilon_spent | 2.41 | 2.41 | 0 | ≤10.0 | ✅ |

## 진단
- **적용 규칙**: D-0X
- **관측 근거**: (metrics.jsonl에서 인용한 실제 수치)
- **기각한 가설**: (검토했으나 배제한 원인과 그 이유)

## 다음 조치
- **변경할 파라미터**: `<name>` <old> → <new>
- **근거 규칙**: D-0X 단계 N
- **예상 효과**:
```

**기록 원칙**: 진단은 반드시 `metrics.jsonl`의 **실제 수치를 인용**해야 합니다.
수치 인용 없는 서술적 진단("학습이 불안정해 보임")은 무효로 간주합니다.

## 5. 에이전트 금지 사항

1. `target_epsilon` / `target_delta` 변경 — 기준을 맞추기 위한 목표 조작
2. 기준 미달 런을 "통과"로 기록
3. 한 번에 2개 이상 파라미터 변경 (단, `hparam_space.json`의 `coupled_with` 예외)
4. `TODO_CONFIRM` 상태의 임계값에 대해 자동 pass/fail 판정
5. 사람 승인 없이 T2 시작
6. TW-05(stall) 발생 시 자동 재시작
7. 규칙 미매칭(D-99) 시 추측에 의한 파라미터 변경
